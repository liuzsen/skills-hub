- lolibaso 是一个非常轻量的 toolkit，可用时优先使用，可按需使用其 sub crates，比如 loso-inject，loso-biz，对大多数项目都适用。
- 明确优于隐含，静态优于动态
- channel 优于 lock
- `abc/mod.rs + abc/a.rs` 优于 `abc.rs + abc/a.rs`，但不把单个 `abc.rs` 改成 `abc/mod.rs`
- 业务层（Domain，Application）的 Error 不应该实现 Error trait，避免：处理输出格式、被轻易转换为 anyhow::Error。

## 错误处理

### 分类与上下文

调用方需要区别处理的失败使用局部错误类型，归维护其失败语义的模块，不使用全局 Error enum。

中需要程序化处理的失败保留明确 enum 类型及结构化上下文，否则使用 `anyhow`，按需添加 `Context`。

可使用 loso-biz 双层 Result 区分`技术错误`和`业务拒绝`，避免 enum 职责混乱

```
pub type BizResult<T, E> = anyhow::Result<Result<T, E>>;
```

#### 传播与转换

内部传播保留原因链，按需补充失败操作的上下文。语义或契约**改变时**转换错误分类，例如将第三方库错误转为模块语言，或将内部失败映射为公开错误。对外隐藏的原因仍保留在内部诊断中。

由决定最终处置错误的位置负责诊断输出，传播与转换时避免重复输出、信息遗漏。错误被恢复、忽略或转为正常结果时，在该处判断是否需要记录。

### 边界与输出

跨进程契约提供稳定错误分类/错误码/结构化数据，程序依赖这些约定，不解析诊断文本来决定行为。

按受众决定输出内容：

- 面向人/LLM的 CLI 展示有助于定位问题的上下文与原因。
- 面向程序的 CLI 在 stdout 输出约定的结构化结果，诊断走 stderr。
- Web / Tauri 返回契约内的分类与数据，由前端决定文案、交互和恢复方式；内部错误链留在服务端诊断中。
