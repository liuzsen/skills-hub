# Dogfood

把 zsen-skills 实际使用中暴露的问题，整理成脱离当前对话仍可判断、可用于改进 zsen-skills 的证据案例。

反馈对象包括安装在项目 `./agents/skills/zsen-skills/` 下的 skills 的指导和随附资源，以及实际使用中暴露、可能需要新增 skill 才能解决的能力缺口。库、工具或项目问题只有暴露这些 skills 的指导、能力或使用障碍，或上述能力缺口时才纳入，不建立独立的库或工具反馈台账。

## 复盘范围

仅由人类调用。复盘整个对话，包括其中 subagent 的相关经历，结合已有变更及验证结果提炼反馈；用户明确限定对象或范围时遵从其限定，不默认扫描整个项目。

由主 Agent 汇总复盘。存在 subagent 时，先查看其已有报告或可访问的会话；若相关使用经历、纠正或证据尚不清楚，按需向原 subagent 采访，了解其实际决策、遇到的障碍、受到的纠正及证据。不要只因最终交付成功，就忽略 subagent 过程中暴露的问题。

采访用于找回实际发生的经历，不要求 subagent 重新执行任务或开展新调查。无法访问的会话、无法联系的 subagent 或无法恢复的证据应明确说明，不推测补齐。

产物按独立案例组织，不写对话流水账。不为补齐案例额外开展调查；已有证据不足之处保留不确定性。

复盘完成后，先提供简要的 dogfood 列表，用户授权写入，或按需深入讨论。

## 筛选案例

关注使用障碍、指导歧义或缺漏、能力缺口、需要反复纠正的用法，以及值得推广但尚未讲清的实践。

任何被人类纠正的行为都值得考虑是否记录，包括已有无歧义指导、Agent 却未遵循的情况。这类案例可帮助改善指导的呈现、可发现性与遵循概率，不应仅因规范已经明确而排除。

区分指导未被遵循、指导难以发现或理解，以及指导本身不适用；原因未明时不要强行归因。一次未遵循不直接证明应增加或改写规范。

筛选有可复用教训的案例，不要求每次纠正都建档。普通进度、项目自身 bug 和无推广价值的琐碎修改不收；它们暴露上游使用障碍时，记录该障碍。没有值得记录的案例就直接说明。

## 证据与判断

- 保存足以独立理解问题的最小代码、输入输出、报错或决策过程。涉及指导时保留相关原文或说明指导缺口；涉及纠正时保留实际行为和人类纠正。
- 文件路径仅作定位，不能替代问题快照；原代码或指导变化后，案例仍须可读。
- 分开表达观察事实、人类反馈、推测原因和改进建议，写清具体影响。
- 区分上游硬约束、推荐风格、项目业务约束与用户偏好，不把局部纠正泛化为普遍禁令。

## 改进建议

指出 zsen-skills 中可澄清、补充、收窄或删除的指导，或随附资源的改进；用最小前后对比和决定性理由说明它如何改善下一次使用。也可建议新增 skill，但需说明现有 skill 为什么不适合承接该能力。建议应注明适用条件与不确定性，尚未实施的方案明确写为建议。

只记录发现当时已有的验证证据。没有足够依据提出改法时，可以仅保留案例与待判断的问题，不强凑建议。

## 落盘

记录保存在项目的 `docs/zsen/dogfood-<skill-name>/`，例如 `dogfood-zsen-engineering/`、`dogfood-lolibaso/`。涉及多个 skill 配合的问题，归入主要改进对象的目录，并在案例中注明其他相关 skill；无法确定主要对象时先确认。没有现有 skill 可归属、建议新增 skill 的案例统一存入 `docs/zsen/dogfood-new-skill/`。

一次调用可提炼多个案例，每篇围绕一个可独立判断、采纳的教训；同类问题补充已有案例，不重复建档。

案例保存发现当时的反馈，不追踪处理状态或采纳进度，不自动成为项目规范，也不自动修改已安装的 Skill 或其他上游内容。是否吸收及如何修改，留待上游审阅。

按需使用以下结构，不要求填满栏目：

```markdown
# 描述具体问题机制的标题

## 场景与证据

任务目标、相关能力或指导、实际行为及最小问题快照；必要的版本、来源与人类纠正。

## 问题与影响

具体后果；区分事实、反馈与推测。

## 改进建议

改法、决定性理由、适用条件，以及已有验证证据与不确定性；无法提出改法时保留待判断的问题。
```

交付前检查：没有当前对话、原文件已经改变时，未来 Agent 能否仅凭案例理解问题，并作出不过度泛化的改进判断？
