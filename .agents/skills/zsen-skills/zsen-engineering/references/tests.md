# 测试与验证

**默认不添加测试**。测试不是严谨的凭证，而是需要维护的代码；测试代码被保留的必要条件是：**能发现难以通过代码审阅发现的错误**。

## 哪些值得测

长期测试聚焦于难以直接审阅确认的复杂逻辑/算法，以及实际暴露且值得防止复发的错误。新增前，先检查现有测试能否覆盖或扩展。

“对外可见”“属于契约”“后果重要”都不能单独成为添加测试的理由。禁止机械地为每个实现文件、接口或 bug fix 都配测试。

- **简单编排不测调用顺序。** UseCase 依次加载、修改、保存，测试再断言三个 mock 按顺序调用，只是在复述实现，不加测试。
- **简单转发不模拟环境。** 文件接口直接调用读写 API，不为它搭建内存文件系统。只需为关键逻辑添加测试即可，比如路径校验。需要确认路径、权限等环境行为时，用真实临时目录定向验证。
- **复杂计算值得测。** 排序规则、解析器、数值算法等难以靠阅读确认所有结果的逻辑，用代表性输入、边界或性质验证，不机械穷举组合。
- **发现真实缺陷，针对根因测。**

## 先优化代码，再考虑测试

类型系统已经保证的性质不再测试；能通过类型或数据结构消除非法状态时，先改表达方式。例如，用 discriminated union 或 enum 表达互斥状态，而不是保留多个布尔值，再测试所有组合。

外部输入使用声明式校验，无需测试，比如 serde::Deserialize 或 zod，而非手写解析 + 测试。

优先从实际被纠正的任务中识别失败模式，再选择防线：类型问题用类型约束，环境假设用真实环境验证，复杂逻辑回归才用测试。

## 不复制复杂环境

如果测试需要重建浏览器、操作系统或外部服务的重要行为，这是在证明模拟环境的正确性，不写这种模拟测试。改用真实环境定向验证，或只测试可独立成立的逻辑。

## 区分探索与回归

为回答当前疑问编写的探索性代码，禁止进入长期测试套件，必要时在文档留下结论、适用环境和依据，而不是保留整个探索过程。

例如，探查 Windows 文件共享标志或某个 API 的实际返回值，是获取认识的实验。只有发现了值得长期防范的失败模式，且能以合理成本有效检出时，才另行提炼为回归测试。

## 控制验证范围

不添加测试不等于不验证。根据本次改动选择最小有效验证，并明确何时结束；优先运行相关已有测试，不默认运行全量检查。通过后，没有相关代码变化或新证据，不重复运行，也不自动升级到更大范围。

## 测试组织

单元测试主体与实现分区，默认放在所属模块的 `tests/` 或 `__tests__/`，按行为主题归并，不机械镜像源码树，也不为每次补丁新增测试文件。

```
a.rs # 自定义测试模块的路径为 tests/a.rs
b.rs
tests/
  a.rs
  b.rs
```
